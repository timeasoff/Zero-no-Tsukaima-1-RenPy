## 1. Языки и приоритет источников

```text
JA = authoritative source of truth   (канон смысла; ps2_source/chapters/*.txt)
EN = base language of the remaster   (база сценария; ПИШЕМ МЫ из JA, готового EN нет)
RU = translation                     (перевод; ПИШЕМ МЫ из JA, опираясь на принятую EN-базу)
```

Готового английского перевода в источнике **нет**. EN — не «эталонный чужой перевод», а
наш собственный текст, лежащий прямо в сценарии (`game/chapters/**/script-*.rpy`).

* смысл проверяется по парам **JA → EN** и **JA → RU**;
* **JA > EN** и **JA > RU** при любом конфликте; расхождение EN ↔ RU не решается молча:
  обе формы проходят по JA, но трактуют по-разному → флаг `RECONCILE` в журнал;
  одна из форм по JA неверна → правится эта форма;
* EN допустимо использовать как **уже принятую интерпретацию** при проверке RU, но
  совпадение RU с EN само по себе не доказательство — доказательство JA;
* ни EN, ни RU никогда не являются доказательством исходного смысла (в том числе текст,
  написанный этой же сессией).

## 3. Единица работы

**Единица итерации — часть главы: файл `game/chapters/<N>/script-ch<N>_<M>.rpy`.**

* глава режется на части `script-ch<N>_1.rpy`, `script-ch<N>_2.rpy`, … по алгоритму ниже;
  глава 1 уже разрезана (10 частей) и **не перерезается**;
* каждая часть правится **тройкой файлов** синхронно:

```text
game/chapters/<N>/script-ch<N>_<M>.rpy   ← EN-текст, voice, *_fx, menu, jump (база)
game/tl/japanese/<bucket>.rpy            ← translate japanese strings: old "EN" / new "JA"
game/tl/russian/<bucket>.rpy             ← translate russian strings:  old "EN" / new "RU"
```

* именование: лейблы `ch<N>` (часть 1), `ch<N>_2`, `ch<N>_3`, …; локации внутри части —
  `<loc>_ch<N>_<M>`; конец части — `jump ch<N>_<M+1>`; конец главы — `jump attention`;
  голоса — `ch<N>_<spk>_<NNN>.ogg` (часть 1) / `ch<N>.<M>_<spk>_<NNN>.ogg` (части 2+),
  нумерация по говорящему с `001`;
* `call overlay_screen(...) from _call_overlay_screen_K` — **`K` уникален во всём
  проекте** (сейчас заняты 1…6, следующий свободный — 7).

Завершённой считается часть, по которой закрыты все пункты `project-checks` и написан
отчёт `reports/ch<N>/<part>.md`.

### Резка главы на части (детерминированный алгоритм)

Ориентир — глава 1: 10 частей / 1244 реплики / 1154 голосовых ≈ **115 голосовых на часть**.

1. Прочитать **всю** главу `ps2_source/chapters/chapter_NN_*.txt` целиком — это границы
   главы. Строка `extra scenes: …` границей главы не является: такие сцены живут **в той же
   части**, где встретились, своим лейблом внутри неё (пример — `date_*_1` в
   `script-ch1_10.rpy`).
2. Накапливать счётчик `[voice N]`; целевой размер части — **115 ± 25** (90…140).
3. Резать только на **сильной границе**, в порядке приоритета:
   * `→ next scene N` (безусловный переход) — сильнейшая граница;
   * смена локации: `[BG stage image=…]` после завершённого блока реплик;
   * конец ветки `【移動】` / `【選択肢】` / `【デート】` (не середина ветки).
4. Окно: резать при накопленных **≥ 90** голосовых; приоритет — первая сильная граница
   после **115**; если к **140** сильной границы нет — резать по ближайшей слабой
   (смена фона); раньше 90 не резать.
5. Уже разрезанные главы не перерезаются.

## 4. Порядок работы над частью

1. Прочитать главу в `ps2_source/chapters/` целиком, затем `ps2_source/events_full/` той же
   главы (точные `set/next/selectItem/dateItem`).
2. Определить структуру: локации, `→ next`, ветки, уводящие в `extra scenes:`.
3. Разрезать на части алгоритмом §3, назначить лейблы, связать `jump`.
4. Портировать по порядку: `*_fx` → `voice` → реплика (EN) → `menu`/`*_choice` → `jump`,
   параллельно дописывая `old/new` в оба `tl/`.
5. Портировать голоса по скиллу `voice-workflow`: `[voice N]` → id → строка
   `voice "…"` → строка `voice_name,voice_id` в `references/voice_id_map.csv`.
   Дорожки уже лежат в `wav_source/`; путь `.STV → wav` — только если id нет в
   `wav_source`. Использованную строку удалить/пометить в `transcriptions_ja_ru.csv`.
   **Финальный этап части** (реплики готовы, пары имя↔id проставлены): подключить
   `.ogg` конвертером — `python tools/media/audio_converter.py convert --apply`
   (отчёт `reports/voice_convert.md`; сверка без записи — подкоманда `check`,
   `reports/voice_check.md`). Только после этого шаг 7: `check_project.py` иначе
   даст E3 «voice без ogg».
6. Перевод: EN-база — в сценарий, JA/RU — в `tl` (скилл `tl-en-ru`, правила `game/PROMTS.md`).
7. Прогнать `python tools/check_project.py` и закрыть чек-лист `project-checks`.
8. Написать отчёт `reports/ch<N>/<part>.md`; решения/сомнения — в `reports/log.md`.

**Очередность порции для git:** `script-ch<N>_<M>.rpy` + `tl/japanese/*` + `tl/russian/*` +
`transcriptions_ja_ru.csv` + `reports/*` — один коммит = одна порция (см. «Git» ниже).

## 5. Правила работы

* **Первичная проверка среды — подготовительный этап, а не отдельная фаза.** Получив
  задание «перевести/портировать главу N», агент в ТОМ ЖЕ запуске проходит
  `ANALYSIS → CLASSIFICATION → PROVISIONAL RESOLUTION → EXECUTION` и начинает первую
  часть. Спрашивать «начинать ли?», возвращать только план или завершаться после
  подготовки — запрещено.
* **Единица записи — файлы проекта** (`*.rpy`, `tl/*`, `reports/*`): пиши их инструментом
  записи и проверяй прочтением. Промежуточных `output/`, `translates/`, `merged/` здесь
  **нет** — не создавай их по привычке.
* **Канал передачи текста.** Кириллицу/японский **не** передавай в аргументах командной
  строки и через конвейеры shell — канал искажает символы. Порядок: напиши текст в UTF-8
  файл инструментом записи → команде передавай только **путь**. После записи прочитай
  файл: не должно быть подмены букв и `?` вместо символов.
* **Кодировка.** PowerShell здесь cp1251: **не печатай** японский/русский в консоль.
  `python -c "…"` с кавычками/переносами ломается — создавай `.py`-файл и запускай
  (готовые утилиты — `tools/`).
* **Все отклонения от источника фиксируются** в `reports/log.md` (удаления, сокращения,
  расхождения JA ↔ EN ↔ RU, сомнения). **Молча ничего не удаляется.**
* **Места, требующие решения человека,** — пометка `???` в отчёте части + запись в журнал.
* **Незарегистрированные сущности называются вслух.** Встретился персонаж без `define`
  в `game/characters.rpy`, фон/CG без строки в `references/image_id_map.csv`, BGM/SE
  без файла или без правила именования (`t{K-1}`, заглушка `id(K)`) — это значит
  **«файла нет / не зарегистрировано»**: отдельный раздел в отчёте части (и запись
  в `reports/log.md`, если решение отложено). Говорящего можно зарегистрировать
  (`voice-workflow` §4.3), но в отчёте он всё равно обязан быть указан; фон/звук —
  не подгонять «на глазок», а отметить и зафиксировать PROVISIONAL/???.
* **Термины — только по `dictionary.md`, обращения — по `addresses.md`.** Словарная запись —
  каноническое лексическое соответствие, а не механическая замена (скилл
  `terminology-dictionary`).
* **Не выдумывай JA-доказательство.** Утверждение «в JA сказано X» требует реального X в
  доступном JA-контексте. Нет точной опоры → «JA прямо этого не подтверждает», пометка
  `???`, запись в журнал.
* **Модальность неприкосновенна.** Вопрос, сомнение, предположение, возможность,
  необходимость, категоричность, степень эмоции не усиливаются и не ослабляются ради
  «естественности».
* **Предпочтение редактора ≠ доказательство ошибки.** Грамматически корректная формулировка,
  сохраняющая смысл по JA и соблюдающая обязательные правила оформления, остаётся.
  Leave-Unchanged Accuracy важнее количества правок; **ноль правок — допустимый итог**.
* **Обратный перевод — диагностический инструмент**, не арбитр над JA: ловит смену
  субъекта/числа/роли и смысловой сдвиг, но по нему нельзя «исправлять» корректный текст.
* **Существующее не переписывается без нужды.** Работа — добавлением: новые главы/строки,
  новые вызовы, новые записи справочников. Архитектурные правки работающего кода — только
  если без них нельзя продолжить, и с записью в журнал.

### Жизненный цикл любого сигнала (обязателен)

Любой сигнал (сканер, скилл, подозрение, ручная находка) проходит:

```text
DETECT → INVESTIGATE → COMPARE → CLASSIFY → DECIDE → EDIT → RECHECK → RECORD
```

**Ни один scanner, pattern, regex или heuristic не разрешает правку сам по себе** —
обнаружение означает только «здесь требуется проверка», а не «это ошибка».

**Classification** (характеристика места): `ERROR` / `WARNING` / `CANDIDATE` / `PASS`.
**Disposition** (судьба кандидата): `FIXED` / `FALSE POSITIVE` / `PRESERVED — FUNCTIONAL`
/ `PRESERVED — JA` / `PRESERVED — CHARACTER VOICE` / `ACCEPTABLE ADAPTATION` /
`USER DECISION` / `???`.
Кандидат, дошедший до решения, обязан получить **оба** значения; формат
«находка → исправлено» без classification/investigation/disposition запрещён. Объединение
нескольких кандидатов — только с явным перечислением всех объединённых. Отчёты различают
detection ≠ classification ≠ investigation ≠ disposition (скилл `russian-style-audit`,
«Отчёты: обнаружение ≠ решение»).

### Неопределённость: UNCERTAINTY ≠ STOP

Неоднозначность сначала классифицируется по масштабу, а не останавливает работу.

* 🟢 **Локальная** (один термин, фраза, название) — не блокирует: исследуй
  JA → `dictionary.md`/`addresses.md` → контекст → этимологию, выбери обоснованную форму,
  пометь `PROVISIONAL`, запиши в журнал, **продолжи**.
* 🟡 **Средняя** (влияет на несколько последующих мест) — не блокирует при traceability:
  временное решение + `PROVISIONAL` + перечень мест использования + продолжение.
* 🔴 **Блокирующая** — только если без решения невозможно корректно продолжить перевод,
  есть риск массового распространения неверного решения или вопрос меняет утверждённый
  канон. Блокируй **минимально возможный участок**, а не всю главу.
* **PROVISIONAL ≠ CANONICAL**: неподтверждённая форма не записывается в `dictionary.md`
  как канон (только с явной пометкой `PROVISIONAL`); путь —
  `PROVISIONAL → USER CONFIRMED → CANONICAL` либо `PROVISIONAL → REJECTED → заменить все
  места использования`. Каждый новый PROVISIONAL-термин указывается в отчёте части.
* **PROVISIONAL ≠ WAIT**: подтверждения не ждут. Отложенные пользователем вопросы —
  статус `OPEN`/`DEFERRED` в `reports/log.md`, не считаются решёнными и разбираются
  отдельным проходом после главы.

### Git: коммит только с явного подтверждения пользователя

**Единое правило приоритетом над всеми локальными инструкциями.** Ни один скилл, скрипт,
подагент или механизм не могут его отменить.

* `git commit` — только после явного подтверждения пользователя на конкретный набор
  изменений. Успешные проверки, «сохранить прогресс», общее разрешение редактировать
  файлы — **не** разрешение на коммит.
* Предложить коммит можно: назвать сообщение и перечень изменений.
* Без подтверждения изменения остаются незакоммиченными.
* `git status`, `git diff`, `git log`, `git show`, сравнение ревизий — разрешены.

### Git vs медиа (`game/INSTRUCTION.md`)

* В git: скрипты `.rpy`, `tl`, `references/`, `reports/`, `tools/`, `ps2_source/`,
  `dictionary.md`, `addresses.md`, `transcriptions_ja_ru.csv`.
* **Не коммитятся**: `audio`, `gui`, `images`, `video` («динамические» папки) и все
  `*.ogg/*.png/*.webp/*.wav/*.webm` — `.gitignore` это уже покрывает; новые голоса живут
  в `game/audio/voices/` локально и в облачном архиве.
* Полное обновление игры = `git pull` + скачать архив медиа из облака и положить в `game/`

## 6. Решения по инфраструктуре (зафиксированы)

| Вопрос | Решение |
|---|---|
| **Бакеты `tl/`** | остаются **плоскими** (`dialogs`, `thoughs`, `choises`, `common`, `overlays`, `characters`, `options`, `screens`) — как в главах 0/1. Разбивать по главам не нужно. Если бакет разрастётся неудобно, допустимо разбить на файлы **внутри того же** `tl/<язык>/` (`dialogs_ch3.rpy`) при условии: одинаковый `old` не встречается дважды (иначе перевод молча не применяется). |
| **`.bak`, `.rpyc.bak`, `dot_checker.py` в `tl/`** | остатки прошлого; `.bak`/`.rpyc` уже в `.gitignore`. Удалять — только по согласованию с пользователем; агенты их не создают и не используют. |
| **`movie(N)`** | в ремастере не реализован (есть только `renpy.movie_cutscene("video/intro.webm")` в `script.rpy`). Вызов пропускается с пометкой `MOVIE not ported` в отчёте части, если видеофайл не добавлен. |
| **`coffee()`** | не реализована → `$ pause(1.0)`; сигнатуру не изобретать. |
| **`item`, `battle*`** | **системы инвентаря и боя ещё не реализованы** (заглушки). Вызовы `item(...)` / `battle*` **не переносятся**; по каждому вызову в отчёте части — строка «не портирован, система не реализована» + собранная информация (предмет, количество, контекст) для возможной будущей реализации. Решение пользователя от 06.10.2026. |
| **«Нереализуемые» вызовы** (`waitAction`, `waitSEStop`, `waitLoad`, `sync`, `create`, `setZoom`, `setRotate`, `setAffineOrigin`, `swapLayers`, `screenShow`, `msgon/msgoff`, `beginSkip/endSkip`) | **не переносятся**; одна строка в отчёте части, чтобы не пересматриваться на каждой главе. |
| **`extra scenes:` / `chapter_90`, `chapter_91` (тундэре/дэре)** | живут в `game/chapters/extra/` (`sp_l1.rpy`, новые `sp_*.rpy`), вызываются из основной линии там, где ссылаются; таблица `dlEventId/tnEventId → label` ведётся в `references/` по мере появления. |
| **`[LAYER lay0 …]`, `[LAYER white …]`** | слой-оверлей: `white` → `flash_fx`; остальные → `flash_fx`/переход по образцу эталона; точечные `x=/y=/setPos/setOpacity/setLevel` не копируются буквально. |
| **`title`-карточки отдельно от текста** (сцены 429, 769) | карточка → `call overlay_screen(...)` с новым уникальным `K`; основной текст — следующей сценой. |
| **Справочник `image id → имя`** | `references/image_id_map.csv` — **генерируется из источника**: `python tools/build_image_id_map.py` (все id фонов/CG: `image_id,kind,filename,source,notes,uses,chapters`). Колонки `filename` и `notes` заполняет **человек**; пока `filename` пуст, в скриптах используется заглушка `id(K)` (`$ fade_fx("id(1145)")`). После заполнения — `python tools/replace_bg_placeholders.py --apply` подставит имена во всех `.rpy`. Контроль — `tools/check_project.py` (E9 битые/дубли строк, E10 неизвестная заглушка, W6 заглушка с уже заполненным именем). Скилл `assets`. |
| **`game/tl/japanese/common.rpy`, `game/tl/russian/common.rpy`** | взяты из документации Ren'Py: **read-only** (атрибут `+R`), не редактировать; из проверок исключены (`tools/check_project.py`, раздел Exceptions) — их ключи участвуют в покрытии E4/E5, но не порождают E6/E8/W1. |
| **Таблица говорящих** | ведётся в `game/characters.rpy` (`define` + `char_data`); полный PS2-список и правило добавления — скилл `voice-workflow`, раздел «Говорящие». |
| **Сцены-заглушки** | сцена 1239 отсутствует в архиве; 12 файлов содержат NUL (стабы без `talk()`) — потери текста нет, портируются как пустые проходы. |

**Что какой пункт закрывает** (полнота инструкции по шагам порта):

| Пункт | Где закрыт |
|---|---|

| Голоса | `voice-workflow` |

| Ассеты (BGM, SE, справочник id, оригиналы) | `assets` |
| Проверка качества | `project-checks` + `tools/check_project.py` |
| Ограничения | `project-constraints` + §1, §5, §6 |

### Порядок слоёв при работе над частью

```text
ps2-source            → разбор источника, границы и структура части
renpy-remaster-api    → соответствие событий, сигнатуры, именование
voice-workflow        → голоса: id → ogg → строка voice
tl-en-ru              → EN в сценарий + old/new в оба tl (параллельно порту)
assets                → BGM/SE/картинки по справочникам
self-review           → самопроверка ПЕРЕД каждой записью
save-progress         → запись + журнал
translation-audit     → смысл JA → EN и JA → RU
semantic-audit-a/b    → независимые смысловые аудиторы (изолированные сессии)
pragmatic-audit       → прагматика реплики (C)
semantic-analyzer     → сводка evidence, classification/disposition
russian-humanizer     → машинность / translationese / AI-штампы (RU)
russian-prose-rules   → оформление русской прозы
russian-grammar-control → грамматика/падежи/актанты/залог
russian-style-audit   → тавтология/повторы/кальки/избыточность
project-checks        → автопроверки + чек-лист приёмки → отчёт reports/ch<N>/<part>.md
```

Слои независимы: каждый ищет свой класс ошибок и не подменяет соседний. Механические
находки (сканеры, pre-check) — **evidence**, а не вердикт: решение принимает
соответствующий скилл в полном цикле жизненного цикла сигнала.

## 8. Отчёты

```text
reports/log.md                  # общий журнал решений (дополняется, не переписывается)
reports/ch<N>/<part>.md         # отчёт по части script-ch<N>_<M>.rpy
reports/check_project.md        # последний прогон tools/check_project.py
reports/voice_check.md          # последний audio_converter.py check (голоса)
reports/voice_convert.md        # последняя конвертация голосов (финальный этап части)
reports/sma/ch<N>/<part>/
    a/  b/  c/                  # evidence независимых аудиторов (<run_id>.md)
    precheck/                   # детерминированная сверка покрытия (evidence, не голос)
    analysis/                   # решения Analyzer (+ phase1)
```

Шаблон отчёта части: источники и границы → соответствие сцен → неперенесённые вызовы
(MOVIE/COFFEE/…) → голоса (манифест, `audio_converter.py`, **нет аудио / нет пары
имя↔id**) → **незарегистрированные сущности** (персонаж без `define`, фон/CG без
строки в `image_id_map.csv`, BGM/SE без файла — отдельным разделом, даже если
говорящий зарегистрирован на этом же шаге) → перевод (EN/RU) → аудиты (по каждому
кандидату: classification + disposition) → PROVISIONAL/??? → чек-лист
`project-checks`.
Отчёты — UTF-8, входят в git. Итоговая сводка по главе — последним разделом отчёта её
последней части.
